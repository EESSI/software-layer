## Contribution guidelines

EESSI welcomes your contributions! To ensure that reviewers can process contributions properly, we've set up these guidelines.

We make a distinction between draft PRs and PRs that are ready to review. Draft PRs are PRs marked as 'Draft' in the GitHub interface. PRs that are ready to review are the ones NOT marked as 'Draft' in the GitHub interface.

PRs that do not follow these guidelines may be closed without detailed review. You are always welcome to address the issues and reopen or resubmit.

### Guidelines for all PRs, regardless of status

- Contributions should always come from GitHub accounts belonging to a human. Fully autonomous AI contributions are not welcome in any shape or form.

### Guidelines for PRs that are ready to review

- Make sure you understand the existing repository, and how it is structured, before adding new code:
    - Are you adding code in the right place?
    - What is the effect of the change on existing functionality?
    - Does the change integrate well with existing code?
- Keep the change easy to review and maintain:
    - Reuse existing code and logic instead of adding parallel implementations.
    - Mimic existing code style.
    - Prefer the simplest solution that works, and favour readable code over compact or fancy code.
    - Keep one logical change per PR and leave out unrelated cleanups. Smaller PRs are generally easier to review.
- If your PR adds a feature, make sure your opening post has a clear description of what feature is added. Some things to think about:
    - What did you want to do that couldn't be done before?
    - How is the new feature expected to behave?
    - How can the new feature be tested (by a reviewer)?
    - Is the feature worth the extra maintenance burden? If a feature with slightly less functionality requires way fewer lines of code / code changes, that might be the preferred option.
- If your PR fixes a bug, make sure it clearly describes the bug:
    - How did you run into the bug (what were you trying to achieve)?
    - How can reviewers reproduce the bug (what was your environment, what did you run)?
    - How can reviewers test the fix?
    - Who would be affected by it?
    - What is the impact (i.e. how 'badly' is something broken)?
- Describe how you tested your change. We don't require that checks run locally, but a change that was never tested by anyone is not ready for review.
- Respond to review feedback by checking whether it applies elsewhere in your PR (or your other PRs), and fix it everywhere, not only where it was pointed out.
- Do not open too many PRs at once:
    - Reviewers have limited time, overwhelming them slows down acceptance.
    - You might make the same mistakes in multiple places, which causes reviewers to spend time twice.
    - There is no hard limit on 'too many': it depends on the complexity of your PRs. Having 10 trivial PRs may be ok, while having 4 complex PRs may be too much.
    - If you are new to the project, start with one PR and wait for feedback before opening similar ones.

### AI specific guidelines

- AI-assisted contributions are allowed, but we _always_ require a human in the loop.
- _You_ are responsible for the contribution.
- Make sure you understand _all_ the code you contribute - whether written by yourself, or an AI assistant. Quiz your AI on what certain code sections do if you don't (fully) understand.
- Make sure you understand all the design choices that were made. Quiz your AI on its design choices until you understand them.
- Do not provide your AI with GitHub tokens that can push comments directly to issues or PRs, and do not otherwise let AI agents participate autonomously in conversations in issues or PRs.
- You _can_ copy responses from AI into a PR / issue comment, but always review the response (is it correct, understandable, complete, does it actually answer the question) before pasting it. Reviewers spend substantial time - respect that time with a real answer. Mark pasted AI text clearly (e.g. start with "AI-generated, reviewed by me:"). Unmarked text is assumed to be your own words.
- If the repository contains an `AGENTS.md`, configure your AI tool to read it (many tools do so automatically; check the documentation of yours).
- You must declare AI use in your PR description, including which tool you used. A short summary (no more than 5-10 short sentences / bullet points) of which parts were done by the AI and which by you is encouraged. You can ask the AI to draft it from your conversation, but review it for accuracy.
- Make sure that whatever change you make, the code is still maintainable without AI in the future.

### Guidelines for draft PRs

- Draft PRs will not receive reviews in general. If a maintainer is interested in what you are doing in a draft PR, they _might_ still comment though.
- You _are_ allowed to open a draft PR for AI-assisted contributions, even if you have not yet reviewed all of the code generated by the AI yourself. Just make sure you do that _before_ marking it ready to review.
- Please close drafts you are no longer working on. Maintainers may close drafts that have been inactive for a long time; you can always reopen them.
